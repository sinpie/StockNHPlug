# 조합 테스트 설계 — 요청 27

요청 원문을 구현 전에 [USER_REQUESTS.md](USER_REQUESTS.md)에 기록했다. 기존 JVM 125개를 유지하고 **새로운 독립 JUnit 케이스 1,000개**를 추가한다. 1,000번의 assertion이나 동일 테스트 반복을 1,000개로 세지 않는다. 전체 입력·기대값은 [케이스 목록](COMBINATION_CASES.md), 기계 입력은 [TSV](../app/src/test/resources/combination-v1.tsv)다.

## 구성과 차원

| ID 범위 | 분야 | 개수 | 조합 |
|---|---|---:|---|
| C0001–C0200 | ROUTE | 200 | 거리 10 × WS 설정 2 × 가격 방향 2 × 타겟/시세 구성 5 |
| C0201–C0400 | ORDER | 200 | 시세 상태 5 × 기존 원장 5 × 실행 상태 4 × 매수/매도 2 |
| C0401–C0600 | LEDGER | 200 | 매수 수량 5 × 수수료 5 × 다른 원장의 소유 범위 4 × 전략 ID 2 |
| C0601–C0800 | EXPORT | 200 | 손익 5 × 문자열 5 × 형식/기간 4 × 날짜 구성 2 |
| C0801–C0900 | SCHEDULE | 100 | 일정 5 × 날짜 5 × 실행 시각 4 |
| C0901–C1000 | ALGORITHM | 100 | 알고리즘 2 × 보유량 5 × 현금 5 × 설정 2 |

목록 입력 a,b,c,d,e는 위 차원 순서다. 불필요한 마지막 자리는 0으로 채운 예약 필드이며 조합 개수에 포함하지 않는다. bool은 0=OFF/1=ON, 색인은 0부터다.

- ROUTE a: 현재가 10,000원 대비 가격차 `[1,100,300,999,1000,1001,1500,2000,3000,4000]`원(0.01%~40%), b=WS 설정, c=-1/+1, d=REST/WS/유효한 근거리+범위 밖 타겟 혼합/모두 상한 밖/모두 하한 밖. 상하한 밖 제시가는 서로 다르게 구성하며 실제 추적가가 범위 안이어도 제시가 제한을 우회할 수 없는지 검사한다. 정적인 거리 구간 기대 간격은 `[2,2,3,5,15,15,15,30,60,180]`초, OFF는 최대 10초, 모든 제시가 범위 밖은 중단. 혼합은 유효한 최근접 타겟을 사용한다. WS 시세와 구독 확인, 캐시 재독의 기한 미연장, 중복 요청 입장 제한도 확인한다.
- ORDER a=최신/거래소 시각 정확히 15초/15초+1ns/수신 미래/비정규장, b=없음/같은 계좌 UNKNOWN/같은 그룹 접수/다른 그룹 접수/다른 계좌 UNKNOWN, c=정상/수량 조회 중 16초 경과/전송 후 응답 불명/시작 후 사용자 정지, d=BUY/SELL. 성공은 메모리 broker의 ACCEPTED이며 실제 체결이 아니다. 전송 직전 SUBMITTING 존재, 타 계좌 원장 불변, 전송 수, 실패 후 UNKNOWN·재시작 재전송 차단을 확인한다.
- LEDGER a=1/2/3/7/20주, b=0/1/3/10/99원, c=다른 계좌/다른 증권사/다른 환경/파킹 예약 그룹, d=물타기/리밸런싱 ID. 주당 10,000원 매수 후 절반 정수 수량을 12,000원에 매도한다. 매수 비용에 수수료 포함, 매도 비용은 수량 비례 정수 배분, 현금·잔여 원가·실현손익 보존, 반복 누적 체결의 멱등성, 종료 보고 후 수량 퇴행 거절을 검사한다.
- EXPORT a=-500/0/500/Long.MAX_VALUE/-Long.MAX_VALUE, b=한글/수식 `=SUM(1,2)`/쉼표·큰따옴표/줄바꿈/수식 `@SUM(1,2)`, c=일 CSV/월 CSV/연 CSV/ZIP, d=2025-12-31~2026-01-03 또는 2026-01-31~02-02. 각각 관측 세 날짜 중 두 날짜만 보고 손익이 있고 한 날짜는 미조회다. 합계는 임의 정밀도 정수 a×2, 빈칸과 0은 구분한다. 입력 목록 제거 후에도 스냅샷 보존, CSV의 종목명 제외, ZIP 종목명 안전 처리·앞자리 0, 인용/줄바꿈을 독립 파서로 확인한다. 앱 파일 쓰기/Android 저장 계약은 여기서 실행하지 않는다.
- SCHEDULE a=평일/매주 월요일/매월 31일/매월 19일/꺼짐, b=2026-03-02·09-21·09-22·09-19·10-01, c=09:59:59·10:00:00·15:14:59·15:15:00(서울). 윤월이 아닌 2월 말일 주말의 3월 이월과 9월 19일 토요일의 21일 이동을 명시적인 기대 날짜 표로 검증한다. 법정 휴장일 계약까지 검증한 것은 아니다.
- ALGORITHM a=물타기/리밸런싱, b=0/1/3/10/20주, c=0/9,999/10,000/50,000/100,000원, d=설정 0/1. 평균가·호가 10,000원, 주문 한도 100,000원. 설정 0은 추가매수 -3%·익절 +6%·누적 매수 2회·밴드 5%p, 설정 1은 -10%·+10%·매수 4회·밴드 10%p, 추가매수 한도는 3회. 리밸런싱 목표 비중은 50%. 정수/유리수 기대식으로 방향·수량·제시가를 검증하고 그룹 ID 변경이 다른 보유량을 끌어오지 않는지 확인한다. 알고리즘 결과는 희망 주문이며 실제 주문 게이트를 대신하지 않는다.

## 기대값과 재현성

`scripts/generate_combination_cases.py`는 프로덕션 코드/API를 호출하지 않는다. 구간 간격 표, 명시한 달력 표, 정수·유리수 비용 보존식을 사용해 TSV와 Markdown을 결정적으로 생성한다. 런타임 구현 함수로 기대값을 계산하여 자신과 비교하지 않는다. 무작위 seed·실시간 시계·외부 API 응답에 의존하지 않으며 각 케이스는 새 객체로 격리된다. 동일한 조합 입력 튜플을 중복 생성하면 실패한다. 같은 결과가 나오는 복합 차단 케이스도 입력이 다른 위험 조합이므로 포함한다.

`CombinationCaseTest.cases`가 리소스를 읽고 ID/개수를 확인한다. JUnit Parameterized가 각 행을 독립 생성한 뒤 `verifyContract`가 분야별 검증기로 보낸다. `MemoryBroker`/`Journal`은 테스트 소스에만 있고 네트워크·키·생산 API를 갖지 않는다. CSV 검증 파서는 내보내기 구현과 별개다. 프로덕션 코드의 위험 게이트/저장 계약은 변경하지 않았다.

```text
python scripts/generate_combination_cases.py --check
./gradlew testDebugUnitTest --tests com.sinpie.stocknhplug.CombinationCaseTest
python scripts/check_combination_results.py
./gradlew testDebugUnitTest lintDebug assembleDebug bundleRelease
```

케이스를 수정할 때 생성 스크립트를 바꾸고 옵션 없이 실행하여 두 파일을 갱신한다. CI는 생성 파일 일치 여부, 전체 JVM 테스트, XML의 1,000개 고유 ID가 누락·중복·실패·오류·skip 없이 실행됐는지를 검사한다. 개별 ID는 예를 들어 `--tests '*CombinationCaseTest*'`로 전체 조합 보고서를 만든 뒤 JUnit XML/HTML에서 C0201을 찾을 수 있다.

## 범위와 한계

선정한 차원들의 직교 조합과 회귀 검사다. 모든 가능한 앱 상태를 망라하는 전수 테스트, 실거래 성공·수익성·무결점 증명이 아니다. 기존 125개 JVM 테스트(연구·파킹·Namu 극값 유지·비동기·복수 계좌 등)를 함께 유지한다. 새 1,000개 중 실제 NH API/WebSocket 서버, 기기 Keystore/SAF, OS 프로세스 종료, 거래소 휴장·결제, 실제 다중 계좌 주문은 실행하지 않는다. 기존 실매매 잠금과 출시 게이트는 유지하며, 실제 결과는 [VERIFICATION.md](VERIFICATION.md)에 별도로 기록한다.
