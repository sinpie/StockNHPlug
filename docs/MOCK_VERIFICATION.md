# 모의계좌 검증 계획과 실제 증거

요청 28: `모의계좌에서 상세하게 모든 기능을 테스트하고 개선해줘.`

## 시험 경계

실제 NH 모의계좌 조회, Android 저장/화면 시험, 가짜 브로커 조합 시험은 서로 다른 증거다. 기존 그룹 체결번호 대사 어댑터와 허가된 뉴스·수정주가 공급자가 없는 상태에서 자동주문을 강제로 실행하지 않는다. 실거래 잠금도 유지한다. 미체결 주문번호를 체결로 간주하지 않는다.

## 실제 키 시험 진입점과 흐름

`CredentialProbeTest.readOnlyOfficialApis`는 `credentialProbe=1`일 때만 disposable debug 설치에서 동작한다. 기본 기기 회귀/CI에서는 제외한다. 일회성 RSA 공개키 → 호스트 메모리 복호화 → AES-GCM 암호문 전달 → Android SecureVault 암호화 저장 → NH MOCK 인증/조회 → 암호문·토큰·계좌 이력 정리 순서다. 원본 INI는 읽기만 한다. 값·응답·계좌번호를 출력하지 않으며 실제 데이터로 만든 CSV/ZIP도 메모리에서만 처리한다.

등록된 모든 모의계좌를 순회하며 잔고, 당일 누적 체결, 최근 손익, 매수/매도 가능수량을 조회한다. 당일 잔고/체결과 손익을 계좌별 EncryptedAccountHistory에 기록하고 재생성한 저장소로 읽어 비교한다. HistoryExport에 실제 이력을 전달해 CSV/ZIP 출력 경로를 실행한다. 이는 외부 문서 제공자 저장 대화상자까지의 시험은 아니다.

시세는 REST 응답과 매매용 신선도 검사를 분리한다. WebSocket ACK, 실제 신선한 틱, 구독 종목 교체, 교체 종목 틱, 명시적 종료 후 새 연결의 ACK/틱을 별도로 판정한다. 제한 시간 내 틱이 없으면 실패이며 휴장/정지 여부는 결과 해석에 별도로 남긴다. ACK만으로 가격 추적 성공을 선언하지 않는다. 명시적 재연결 시험은 네트워크 단절 자동 복구나 장시간 백그라운드 보장이 아니다.

단계별 실패를 누적하고 정리 후 JUnit 전체 실패로 반환한다. 계좌 목록이 비어 있어도 실패한다. `local_cleanup=PASS`는 검증 성공과 다르며 `overall=PASS`를 함께 확인해야 한다.

| 기능 | 실제 API/기기 검증 | 모형 회귀 및 제한 |
|---|---|---|
| 키·인증 | 암호문 전달, Keystore, NH/OpenDART | 훼손 거절, 계좌별 AAD |
| 잔고·보유·체결·손익 | 반환된 모든 모의계좌 조회 | 실제 주문 생성·체결 대사는 별도 |
| 이력·통계·다운로드 | 실제 이력 암호화 저장/복원·메모리 CSV/ZIP | SAF UI/오류 회귀는 합성 데이터 |
| REST/WS | 현재가 검증·틱·교체·재연결 | 10% 경계·간격·OFF 10초·상하한가·날짜 연속성은 결정적 회귀 |
| 전략·그룹·추천·정기매수 | 자동주문 시작 게이트 유지 | 물타기/리밸런싱·그룹 소유권·일정 조합; 실제 매수 미검증 |
| 파킹·위험·미확인 주문 | 실제 주문 미실행 | 누적 체결·현금 갱신·사전 원장·재전송 금지 회귀 |
| 복수 계좌 동시 실행 | 반환된 계좌 수에 한정 | 여러 runtime 동시 시작/정지·부분 시작 취소는 가짜 runtime |
| 화면·비동기·보안 | disposable Android 회귀 | 장시간 Doze·실물 기기·Play 심사 별도 |

## 발견한 문제와 개선

- NhBroker의 `available`, `executions`, `dailyPnl`에도 `portfolio`와 동일한 계좌 환경/증권사 일치 검사를 추가했다. 가능수량 조회의 종목 형식/양수 가격도 검사한다. 상위 계층뿐 아니라 어댑터 직접 호출도 네트워크 전에 거절한다.
- `BrokerBoundaryTest`가 키 없이 다른 환경/증권사 조합의 계좌별 조회를 호출하여 인증 시도 이전의 IllegalArgumentException을 확인한다.
- 기존 진단의 첫 계좌만 검사/ACK만 검사/실패 후 녹색 JUnit 문제를 위 흐름으로 개선했다.
- 실제 두 번째 시험에서 HTTP 429 1건을 관측했다. NhRequestPacer가 이후 호출에 2초 대기와 30초간 1초 간격을 적용하도록 추가했다. 기본 250ms 간격은 유지하며 실패 요청의 자동 재시도/토큰 재발급은 없다. 외부에서 같은 키를 사용하는 다른 프로그램의 호출량까지 제어하는 것은 아니다.
- 가능수량 조회를 매매용 시세 신선도 검사와 분리했다. 공식 현재가의 종목/양수 가격만 조회 입력으로 사용하며 주문하지 않는다. 별도 현재가 검증 실패는 전체 진단 실패로 그대로 남긴다.

## 실행 결과

2026-09-21 서울 장중, API 30 disposable 설치에서 사용자 제공 암호화 키를 이용해 3회 실행했다. 계좌 목록은 3개였다. 세 번 모두 정리 성공, 전체 진단은 실패다. 실패를 없애기 위해 신선도 기준/계좌 검사를 완화하거나 주문을 우회 실행하지 않았다.

| 실행 | 관측 결과 |
|---|---|
| 1 | 3계좌 잔고·체결·손익·이력 출력 통과. 2/3계좌 가능수량 단계가 선행 시세 검증에서 실패하여 해당 가능수량 API는 미실행. REST 매매용 검증 거절. WS 틱/교체/재연결·NH 인증·OpenDART 통과 |
| 2 | 가능수량을 분리한 후 모든 계좌 매수/매도 가능수량 통과. 2번 계좌 첫 잔고 조회 HTTP 429. REST 가격/양방향 호가/상하한가/정규장 표시는 유효하지만 신선도 검사 NO. WS와 이력 출력 통과 |
| 3 (감속 보완 후) | 모든 계좌 잔고·체결·가능수량·이력 출력 통과. 3번 계좌 첫 손익 조회 HTTP 429. 별도 이력 검증 단계의 손익 조회는 통과했으나 앞선 실패를 지우지 않음. REST 신선도·매매용 검증, WS 틱/교체/재연결, 일봉, 공시·연결재무 통과 |

429 후 감속의 계산·회복 경계는 JVM 테스트로 검증한다. 이후 429가 다시 없었다는 관측만으로 정책 효과/한도 준수/외부 프로그램 영향까지 입증하지 않는다. 실제 키 시험은 계좌 조회·시세 통합 증거이며, 3계좌 자동매매 동시 운용이나 실제 주문·체결 시험이 아니다. 일봉은 여전히 adjusted=false다. 외부 웹 가이드 재조회는 timeout이었으며 새 로그인 필요 여부를 확인한 것으로 기록하지 않는다.

최종 로컬 빌드 및 Android 결과는 [VERIFICATION.md](VERIFICATION.md)에 기록한다.
